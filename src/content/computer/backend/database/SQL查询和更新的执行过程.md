一条 SQL 发给 MySQL 之后，数据库并不是直接去磁盘里查找或修改数据。它需要依次完成连接管理、语句解析、执行计划选择和数据访问；更新语句还要借助事务日志保证数据能够恢复，并与 binlog 保持一致。

从整体上看，MySQL 可以分为两层：

- **Server 层**负责连接管理、SQL 解析、查询优化和执行等通用能力，也包含存储过程、触发器、视图等功能。
- **存储引擎层**负责数据的存储和读取，并通过统一接口向 Server 层提供能力。常用的 InnoDB 就是一个存储引擎。

## 建立连接

执行 SQL 之前，客户端需要先与 MySQL 服务端建立连接。例如：

```bash
mysql -h 127.0.0.1 -P 3304 -u root -p -D example_db
```

这里的 `-h`、`-P`、`-u` 和 `-D` 分别表示主机、端口、用户名和默认数据库；`-p` 表示交互式输入密码。为了避免密码出现在终端历史和进程列表中，不要把密码直接写在 `-p` 后面。

MySQL 的**连接器**负责建立和管理客户端连接，包括身份认证、连接状态维护以及权限信息的读取。连接建立成功后，如果管理员刚刚修改了该用户的权限，已有连接通常不会自动刷新权限信息，需要重新连接后才会生效。

## 查询缓存：MySQL 8.0 已移除

旧版本 MySQL 曾提供 Server 层查询缓存：它以 SQL 文本为键缓存完整结果，命中后可以直接返回。不过，只要相关表发生更新，该表对应的缓存就会失效。对于写入频繁的业务表，缓存维护成本高且命中率低，因此它并不适合大多数业务场景。

查询缓存从 MySQL 5.7.20 开始被标记为弃用，并在 MySQL 8.0 中彻底移除。因此，讨论 MySQL 8.0 的执行流程时，可以直接从连接器进入解析阶段。应用缓存和 CDN 也不等同于 MySQL 查询缓存：它们处于不同层级，拥有不同的失效策略和适用范围。

## 解析与预处理

连接建立后，MySQL 会对 SQL 进行解析和预处理，这一阶段可以拆成三个部分：

1. **词法分析**：识别 SQL 中的关键字、表名、列名、常量和运算符等 token。
2. **语法分析**：按照 SQL 语法规则检查 token 的组合，并构造语法树。关键字拼错、括号不匹配等问题通常会在这里产生语法错误。
3. **预处理与语义检查**：解析表和列等对象，检查列是否存在、名称是否存在歧义，并完成相应的权限检查。常见的 `Unknown column` 并不是词法分析错误，而是在名称解析过程中发现的。

经过这一阶段，MySQL 已经理解了这条 SQL 想要查询或修改什么。

## 优化器选择执行计划

同一条 SQL 往往有多种执行方式：可以使用不同的索引，可以选择全表扫描，多表关联时还可以采用不同的连接顺序和连接算法。**优化器**的任务就是从候选方案中选择一个执行计划。

传统上，优化器通常分为两类：

- **RBO（Rule-Based Optimizer）**：根据预先定义的规则选择执行计划。
- **CBO（Cost-Based Optimizer）**：结合表的统计信息和成本模型，估算不同执行计划的 CPU、内存与 I/O 成本，选择预计成本最低的方案。

MySQL 8.0 使用的是以成本为基础的优化器。我们通过 `EXPLAIN` 看到的访问类型、索引选择、预估扫描行数和连接顺序，就是优化器生成的执行计划。需要注意的是，成本来自统计信息和估算，成本最低的计划不一定总是实际执行最快的计划。

## 执行器与存储引擎

执行计划确定后，**执行器**开始执行。它会根据计划调用存储引擎提供的接口，例如读取索引中的第一条记录、读取下一条记录或根据主键查找记录。

以一个带条件的查询为例，执行器可能会重复进行以下操作：

1. 请求 InnoDB 读取一条记录；
2. 判断记录是否满足查询条件；
3. 满足条件时放入结果集；
4. 继续读取下一条记录，直到查询结束；
5. 将最终结果返回客户端。

数据页不一定每次都从磁盘读取。InnoDB 会优先在 Buffer Pool 中查找所需页面，未命中时才需要从磁盘加载。因此，“执行器调用存储引擎”和“发生磁盘 I/O”并不是同一件事。

## 更新语句如何执行

更新语句同样要经过连接器、解析与预处理、优化器和执行器。区别在于，InnoDB 找到目标记录后还需要完成事务修改和日志记录。以一条 `UPDATE` 为例，其核心流程如下：

1. 执行器根据执行计划调用 InnoDB，找到需要更新的记录；
2. InnoDB 在修改数据前记录 undo log，用于事务回滚和 MVCC；
3. InnoDB 在 Buffer Pool 中修改数据页，被修改的页面成为脏页，之后再由后台线程刷入磁盘；
4. InnoDB 写入 redo log，并将事务状态置为 `prepare`；
5. Server 层写入 binlog；
6. InnoDB 将 redo log 状态改为 `commit`；
7. 执行完成，结果返回客户端。

其中，redo log 是 InnoDB 的引擎日志，主要用于崩溃恢复；binlog 是 Server 层的归档日志，常用于主从复制和数据恢复。MySQL 使用两阶段提交协调两种日志，避免数据库崩溃后出现 redo log 与 binlog 不一致的问题。

> 这里省略了组提交、刷盘策略和异常恢复等细节，后续会在《redo log、binlog及两阶段提交》中展开。

## 小结

一条查询语句的主要链路是：

```
客户端 → 连接器 → 解析与预处理 → 优化器 → 执行器 → 存储引擎 → 返回结果
```

更新语句会复用这条 Server 层链路，但在存储引擎修改数据时，还要记录 undo log、redo log 和 binlog，并通过两阶段提交保证日志一致性。理解这条路径，是继续分析索引选择、慢查询、锁等待和事务问题的基础。
