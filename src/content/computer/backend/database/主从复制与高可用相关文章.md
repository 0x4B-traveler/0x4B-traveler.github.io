MySQL 的主从复制（在新版本文档中也称 source/replica replication）并不是主库把数据文件直接复制给备库，而是主库把事务变更写入 binlog，备库接收并重放这些逻辑事件。理解这条链路，才能解释主备延迟、复制一致性、故障切换和循环复制问题。

本文聚焦三个问题：事务日志如何从主库同步到备库、三种 binlog 格式分别记录什么、主主或级联拓扑中如何避免循环复制。

## 一、事务日志同步的完整过程

### 1. 主库提交事务

以 InnoDB 为例，一条更新语句在主库上的关键路径如下：

```text
客户端提交事务
      │
      ├─ InnoDB 修改 Buffer Pool，写 undo log
      ├─ InnoDB 写 redo log，标记 PREPARE
      ├─ Server 将事务事件写入 binlog
      ├─ 按 sync_binlog 配置刷 binlog
      └─ InnoDB 将 redo log 标记 COMMIT
            │
        返回客户端
```

redo log 用于 InnoDB 崩溃恢复，binlog 用于复制和按时间点恢复。两份日志必须对同一个事务做出一致判断，因此使用两阶段提交：redo 先进入 PREPARE，binlog 完成后再把 redo 标记为 COMMIT。主库返回成功前，是否等待日志真正落盘由 `innodb_flush_log_at_trx_commit` 和 `sync_binlog` 等参数决定。

### 2. binlog dump 线程发送事件

主库为每个副本维护一个 binlog dump 线程。副本连接主库后，会发送自己的复制位点（传统复制使用文件名和 position，GTID 复制使用 GTID 集合），主库从该位置读取 binlog 事件并通过复制连接发送。

主库发送的是事务事件流，而不是数据页。一个事务通常包含 GTID（启用 GTID 时）、`BEGIN`、若干行或语句事件、事务提交事件等。事务的事件顺序必须保持，副本才能按相同顺序重放。

### 3. 副本接收并写入 relay log

副本上的 I/O 接收线程（新文档称 receiver）把主库发来的 binlog 事件写入本地 relay log，并更新 relay-log 的读取位置。relay log 是副本的中间缓冲：即使 SQL 应用线程暂时跟不上网络接收，已经收到的事件也不会丢失。

```text
主库 binlog
    │ 复制连接
    ▼
副本接收线程 ──> relay log 文件
```

relay log 的持久化策略也会影响故障后的恢复边界。需要较强持久性时，应评估 `sync_relay_log`、`sync_relay_log_info` 以及副本崩溃恢复设置，而不是只关注主库的 `sync_binlog`。

### 4. SQL 应用线程重放事务

副本 SQL 线程（或并行复制 worker）按 relay log 中的事件执行：

```text
relay log
    │
    ▼
SQL coordinator
    │
    ├─ 串行应用：一个线程按顺序执行
    └─ 并行应用：多个 worker 按依赖关系执行
           │
           ▼
       副本 InnoDB
```

应用完成后，副本会更新自己的 relay-log-info 和执行位点。主库的 `Seconds_Behind_Source` 只能作为粗略参考，不能证明数据已经完全一致；更可靠的检查还应比较 GTID 集合、事务位点和业务校验结果。

### 5. 异步复制与半同步复制

默认复制是异步的：主库提交成功不需要等待副本应用完成，因此主库吞吐量高，但主库突然故障时可能丢失尚未传输或尚未持久化的事务。

半同步复制会要求至少一个副本返回确认。这个确认点要看具体配置：常见实现是在副本收到并持久化 relay log 后确认，而不是等 SQL 线程把事务执行完。半同步可以缩小故障丢失窗口，但会把网络延迟和副本 I/O 延迟加入主库提交路径；它也不能替代故障切换、数据校验和应用层幂等设计。

## 二、binlog 三种格式的完整示例

假设有表：

```sql
CREATE TABLE account (
  id BIGINT PRIMARY KEY,
  balance DECIMAL(10, 2),
  updated_at TIMESTAMP
);

INSERT INTO account VALUES (1, 100.00, '2026-09-05 10:00:00');
```

执行：

```sql
UPDATE account
SET balance = balance - 10,
    updated_at = NOW()
WHERE id = 1;
```

### 1. STATEMENT：记录原始 SQL

配置：

```ini
binlog_format = STATEMENT
```

binlog 中记录的核心事件可以理解为：

```text
GTID  source-uuid:101
BEGIN
Query: UPDATE account
       SET balance = balance - 10, updated_at = NOW()
       WHERE id = 1
COMMIT
```

副本收到后重新执行这条 SQL。优点是日志体积小、网络传输量少；问题是 SQL 必须在主库和副本上产生完全相同的结果。`NOW()`、`UUID()`、非确定性函数、依赖当前时间或未明确排序的语句，都可能导致主备结果不同。即使 MySQL 对部分语句写入额外的上下文信息，也不能把所有复杂语句都安全地归入 statement 格式。

### 2. ROW：记录行的前后镜像

配置：

```ini
binlog_format = ROW
```

ROW 格式不要求副本重新计算 `NOW()`，而是记录受影响行的变化。概念化的 `mysqlbinlog -vv` 输出如下：

```text
GTID  source-uuid:101
BEGIN
Table_map: db.account
Update_rows: table id 42
### UPDATE `db`.`account`
### WHERE
###   @1=1
###   @2=100.00
### SET
###   @1=1
###   @2=90.00
###   @3='2026-09-05 10:01:02'
Xid = 101
COMMIT
```

副本直接把指定行改成 after image，结果不依赖副本执行时的当前时间和函数值，一致性通常更好。代价是更新大量行时 binlog 可能明显变大；`binlog_row_image` 还会影响记录的是 full、minimal 还是 noblob 行镜像，不能只看 SQL 文本估算日志量。

### 3. MIXED：按语句风险自动选择

配置：

```ini
binlog_format = MIXED
```

对于确定性较高的语句，MIXED 可能记录 statement 事件：

```text
BEGIN
Query: UPDATE account SET balance = balance - 10 WHERE id = 1
COMMIT
```

检测到可能产生主备差异的语句时，MIXED 会切换为 row 事件，例如：

```text
BEGIN
Table_map: db.account
Update_rows: ...
  before: id=1, balance=100.00
  after : id=1, balance=90.00
Xid = 101
COMMIT
```

MIXED 的目标是在日志体积与安全性之间折中，但“自动选择”增加了排查复杂度，不能保证所有业务语句都符合预期。实际生产环境通常优先使用 ROW，并配合主键、唯一键、合理的行镜像配置和日志容量监控。

### 三种格式对比

| 格式 | binlog 记录 | 主要优点 | 主要风险 |
| --- | --- | --- | --- |
| STATEMENT | 原始 SQL | 日志小、可读性强 | 非确定性语句可能导致主备不一致 |
| ROW | 行的 before/after 镜像 | 结果稳定，复制安全性高 | 日志可能变大，批量更新放大 I/O |
| MIXED | 按语句风险自动选择 | 兼顾体积和安全性 | 行为不够直观，边界场景仍需验证 |

## 三、如何避免循环复制

循环复制发生在一个事务从实例 A 复制到 B 后，又被 B 当作新事务转发回 A，或者在多级拓扑中沿环路重复传播。它可能造成重复执行、binlog 无限增长和复制线程反复报错。

### 1. 使用唯一的 server_id

每个参与复制的实例都必须设置不同的 `server_id`：

```ini
# A
server_id = 101

# B
server_id = 102
```

副本收到事件后，会检查事件中的来源 server ID；当发现事件已经来自自己的 `server_id` 时，默认不会再次应用，从而阻断最基本的回环。`server_id` 必须全局规划，不能只保证同一对主备不重复。

### 2. 正确配置级联复制

如果 B 既是 A 的副本，又要为 C 提供复制，B 必须记录从 A 收到的 binlog 事件，并把它们继续提供给 C。旧版本参数名是 `log_slave_updates`，新版本使用 `log_replica_updates`：

```ini
log_replica_updates = ON
```

这不是“关闭循环检查”，而是允许级联拓扑传播已应用事务。B 继续向 C 发送时，事件仍保留原始事务信息，C 不应把它误认为由 B 重新产生的独立事务。

### 3. 使用 GTID 和自动定位

GTID 为事务分配全局标识，例如：

```ini
gtid_mode = ON
enforce_gtid_consistency = ON
log_replica_updates = ON
```

副本连接时发送自己已经执行过的 GTID 集合，主库只发送缺少的事务。相比手工维护文件名和 position，GTID 能更清楚地识别“这个事务已经在环路中的其他节点执行过”，也更适合主备切换和多级复制。

### 4. 复制过滤只能作为边界防护

`replicate_do_db`、`replicate_ignore_table` 等过滤规则可以减少不需要复制的数据，但它们不是通用的循环复制方案，尤其在 STATEMENT 格式下，过滤判断可能受当前默认库和 SQL 执行上下文影响。过滤配置应在变更前用实际 binlog 事件验证，并记录在拓扑文档中。

### 5. 操作建议

1. 为每个实例分配唯一 `server_id`，并为 GTID、复制账号和过滤规则建立配置清单。
2. 变更拓扑前先确认 `SHOW BINARY LOG STATUS`、`SHOW REPLICA STATUS` 和 GTID 集合。
3. 主主复制不等于双写安全；应用仍需避免同一行被两个主库同时修改，必要时使用单写主库或冲突检测。
4. 故障切换后，先确认新主库已经包含旧主库的全部可用事务，再修改复制方向，避免把旧主库的陈旧数据重新灌回拓扑。
5. 定期执行校验工具或业务抽样校验，不能只以“复制线程显示 Running”作为一致性证明。

## 小结

- 主库通过 binlog 发送事务，副本经过接收线程、relay log 和 SQL 应用线程完成重放。
- redo log 负责本地崩溃恢复，binlog 负责跨实例复制；异步复制不保证主库提交后副本立即完成应用。
- STATEMENT 记录 SQL，ROW 记录行镜像，MIXED 根据风险在二者间选择；生产环境通常优先 ROW。
- 唯一 `server_id` 是回环检测基础，GTID 负责事务级别的自动定位与去重，`log_replica_updates` 用于级联传播而不是关闭回环保护。
- 主备一致性需要日志持久化、复制状态、拓扑配置和业务校验共同保证。

## 四、主备延迟：把现象拆成具体时间点

主备复制达到的是最终一致性，而不是主库提交后备库立即可见。为了定位延迟，先把同一个事务拆成三个时间点：

```text
主库 A：事务执行完成并写入 binlog ── T1
                         │ 网络传输
备库 B：接收完成并写入 relay log ──── T2
                         │ SQL 线程/worker 重放
备库 B：事务执行完成 ───────────────── T3

主备延迟 = T3 - T1
网络或接收延迟 = T2 - T1
备库应用延迟 = T3 - T2
```

这三个时间点对应三种完全不同的排查方向：T2-T1 大，优先看网络、主库 dump 线程和备库接收/relay log 写入；T3-T2 大，优先看备库 CPU、磁盘、锁等待、事务大小和并行复制能力。

`SHOW REPLICA STATUS\G` 中的 `Seconds_Behind_Source`（旧版本为 `Seconds_Behind_Master`）可以帮助观察趋势，但它不是端到端一致性的证明。它依赖 binlog 事件中的时间信息，复制线程停止、网络中断、时间不同步或正在执行长事务时，可能出现 `NULL` 或不能准确反映真实业务可见延迟。因此，切换前还应比较 GTID 集合或明确的事务位点。

## 五、主备延迟的场景化分析

### 场景 1：备库机器比主库弱，或多个备库争抢同一台机器

更新在主库和备库都会产生读、写、刷脏页和索引维护。备库即使没有业务查询，也需要消耗与重放相匹配的 CPU 和 I/O。如果把多个主库的备库集中在一台低规格机器上，relay log、数据文件和多个复制线程会争抢磁盘队列，延迟会持续增加。

```text
主库 A（16 核、SSD） ──> 备库 B（4 核、普通磁盘）
主库 C（16 核、SSD） ──>      ↑
                           多个复制任务争抢资源
```

改进方式：主备尽量对称部署，至少保证备库能够承受故障切换后的写入；对多主多备拓扑按实例分散机器，并监控 CPU、IOPS、I/O latency、buffer pool 命中率和复制线程耗时。

### 场景 2：备库承担了过多读请求、报表或备份

读写分离后，团队容易把备库当成“免费的查询机器”。一个没有合适索引的报表查询可能扫描大量页面，和 SQL worker 争抢 CPU、Buffer Pool 以及磁盘 I/O；全量备份、校验和大范围排序也可能造成同样的问题。

```text
备库 B 的资源池
├─ 复制 SQL worker：应用 relay log
├─ 业务读请求：扫描和排序
├─ 报表/分析：长时间占用 CPU
└─ 备份任务：持续读取数据文件
```

改进方式：一主多从，把高并发读和备份分散到不同副本；将分析类查询导出到数仓或其他下游系统；对备库设置连接、资源和查询时限，避免让复制线程与非核心任务无限竞争。

### 场景 3：主库的大事务把延迟集中到提交点

主库事务通常要在完成后才形成完整的 binlog 事务事件。比如一次删除几千万行的事务，主库可能执行数分钟；备库在收到它之前看不到这批变更，收到之后又要执行很长时间，于是延迟会突然跳高。

```sql
-- 高风险示例：单事务删除大量数据
DELETE FROM orders WHERE created_at < '2024-01-01';
COMMIT;
```

更安全的做法是按主键范围分批删除，每批控制行数和事务时长，并在低峰执行。大表 DDL 也要谨慎：即使 DDL 在主库侧看起来很快，备库应用时仍可能阻塞其他事务，造成复制队列堆积。

### 场景 4：备库并行复制能力不足

单线程 SQL 应用时，主库可以并发提交多个互不相关的事务，备库却必须串行执行。升级硬件不能解决事务依赖本身造成的队列，尤其是大量事务集中更新同一个库、同一张表或相邻索引页时。

```text
主库：T1 ─┐       ┌─ T3 ─┐
          ├─并发──┤      ├─ 写入 binlog
       T2 ─┘       └─ T4 ─┘

备库单线程：T1 -> T2 -> T3 -> T4
备库并行：  T1 ─┐
             T2 ─┼─ 按依赖关系并发
             T3 ─┘
```

应根据版本启用并行复制并观察实际收益，例如按逻辑时钟或 writeset 识别可并行事务。并行 worker 并不是越多越好：worker 过多会增加调度、锁竞争和上下文切换，最终可能比串行更慢。

### 场景 5：网络、relay log 磁盘或复制异常

网络丢包、带宽不足、主库 dump 线程阻塞、备库 relay log 所在磁盘空间不足，都会使 T2-T1 变大。若接收线程停止，通常先看 `Replica_IO_Running`、连接错误和 relay log；若接收正常但应用落后，重点看 `Replica_SQL_Running`、锁等待和执行位点。

排查的最小信息集：

```sql
SHOW REPLICA STATUS\G
SHOW BINARY LOG STATUS;
```

重点记录 `Replica_IO_Running`、`Replica_SQL_Running`、`Seconds_Behind_Source`、`Relay_Source_Log_File`、`Exec_Source_Log_Pos`、`Retrieved_Gtid_Set` 和 `Executed_Gtid_Set`。不能只看复制线程是否为 `Yes`：线程“在运行”只表示它没有明显报错，不代表它已经追平主库。

## 六、双 M 结构与主备切换流程

高可用系统常把 A、B 配置成双 M：两边都具备主库能力，也都保留复制配置，但正常情况下只允许一个节点接收业务写入。这样故障切换后，可以把原备库 B 提升为主库，再把恢复后的 A 作为 B 的副本。

```text
正常状态（单写）
业务写入 ─────> A（主库） ──binlog──> B（备库）
                  ▲                  │
                  └────复制配置──────┘

切换后（单写）
业务写入 ─────> B（新主库） ──binlog──> A（恢复后备库）
```

双 M 不等于两个节点可以安全地同时写同一行。双写会引入冲突、唯一键错误和回环风险；除非有明确的分片键、冲突检测和业务幂等策略，否则仍应坚持单写主库。

## 七、两种切换策略：可靠性优先与可用性优先

### 可靠性优先：宁可多等一会儿，也不主动丢事务

适用于订单、支付、库存等不能接受数据回退的业务。以 A 故障前的主动切换为例：

```text
1. 停止或冻结 A 的业务写入
2. 等待 B 接收并执行完 A 的全部 binlog
3. 比较 GTID/位点，确认 B 已追平
4. 将 B 提升为新主库并切换连接入口
5. 修复 A，清理旧复制关系
6. 让 A 从 B 重新建立副本关系
```

这套流程会产生短暂不可写窗口，但切换后的 B 包含 A 已确认提交的事务，数据一致性边界更清楚。自动化系统应设置超时和人工介入点：如果 B 长时间追不上，不应为了“完成切换”盲目强制提升。

### 可用性优先：先恢复写入，再接受明确的数据风险

适用于更看重快速恢复、且业务可以补偿或重放的场景。假设 A 比 B 多执行了事务 `c=4`，但该事件还没有应用到 B：

```text
A：1 -> 2 -> 3 -> 4    （事务 4 只存在于 A）
B：1 -> 2 -> 3          （提升为新主库）

B 接收新请求：写入 5
B：1 -> 2 -> 3 -> 5
```

此时如果旧 A 恢复并把未同步的 4 重新灌入 B，可能出现顺序冲突、业务状态回退或唯一键错误。选择可用性优先时，必须记录丢失事务范围，设计补偿、人工核对和旧主库隔离流程，不能把“切换成功”当成“数据没有损失”。

## 八、从监控到处置的排障流程

```text
发现 Seconds_Behind_Source 上升
              │
              ▼
先判断 T2-T1 还是 T3-T2 变大
       ┌──────┴──────┐
       ▼             ▼
网络/接收链路       备库应用链路
检查 IO 线程、       检查 SQL worker、
带宽、relay log      锁等待、事务大小、
磁盘和空间           并行复制和读压力
       └──────┬──────┘
              ▼
确认是否可追平，再决定限流、迁移读流量、拆分事务或切换
```

建议把延迟监控拆成三类指标：接收位点与主库写入位点的差距、应用位点与接收位点的差距、业务实际可见数据的校验结果。对延迟持续上升、延迟突然尖峰和复制线程报错，分别设置不同告警阈值；单一的 `Seconds_Behind_Source` 不足以支撑高可用决策。

## 小结

- 主备延迟应拆成 T1、T2、T3，分别定位主库生成、网络接收和备库应用三个阶段。
- 备库硬件弱、读/备份压力、大事务、并行复制不足、网络和 relay log 问题，对应的排查路径不同。
- 双 M 结构的核心是故障切换后的角色复用，不代表允许两个节点同时无冲突写入。
- 可靠性优先会等待备库追平，可用性优先可能丢失尚未同步的事务；两者都必须显式记录风险。
- 高可用不是一个参数，而是复制日志、延迟监控、切换流程、数据校验和业务补偿共同构成的系统。
