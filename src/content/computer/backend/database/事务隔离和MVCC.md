## 事务隔离级别

事务的隔离性，就是 ACID 中的 **I（Isolation）**。当多个事务同时读写数据库时，隔离性决定了一个事务能够在多大程度上看到其他事务产生的中间状态或已经提交的结果。

隔离程度越高，并发事务之间相互影响的可能性越低，但数据库需要付出的协调成本通常也越高。因此，事务隔离本质上是在**数据一致性**和**并发性能**之间做权衡。

### 并发事务可能产生的问题

理解隔离级别之前，需要先认识三种常见的并发读取异常：

- **脏读（Dirty Read）**：一个事务读到了另一个尚未提交的事务所修改的数据。如果后者回滚，前者读到的就是从未真正生效的数据。
- **不可重复读（Non-repeatable Read）**：同一个事务先后读取同一行，得到的结果不同，因为这期间另一个事务提交了对该行的修改或删除。
- **幻读（Phantom Read）**：同一个事务按照相同条件查询两次，结果集的行数不同，因为这期间另一个事务插入或删除了符合条件的记录。

不可重复读关注的是**同一行内容发生变化**，幻读关注的则是**符合查询条件的记录集合发生变化**。

### SQL 标准定义的四种隔离级别

SQL 标准定义了四种事务隔离级别，隔离程度由低到高依次为：

| 隔离级别 | 能否读到未提交数据 | 同一行能否重复读取 | 是否允许出现幻读 | 特点 |
| --- | --- | --- | --- | --- |
| 读未提交（READ UNCOMMITTED） | 可能 | 不保证 | 可能 | 并发能力强，但可能发生脏读 |
| 读提交（READ COMMITTED） | 不能 | 不保证 | 可能 | 每条语句只能看到执行前已经提交的数据 |
| 可重复读（REPEATABLE READ） | 不能 | 保证 | SQL 标准下仍可能 | 同一事务中的快照读保持一致，是 InnoDB 的默认级别 |
| 串行化（SERIALIZABLE） | 不能 | 保证 | 不允许 | 事务近似串行执行，隔离最强，并发能力最低 |

#### 读未提交

在读未提交级别下，一个事务尚未提交的修改就可能被其他事务看到。因此它可能产生脏读、不可重复读和幻读。虽然限制最少，但数据一致性很难保证，业务系统通常不会选择这个级别。

#### 读提交

在读提交级别下，一个事务只能看到其他事务已经提交的修改，因此不会发生脏读。不过，每条查询语句都可能看到一个新的已提交数据状态，所以同一事务内连续执行两次相同查询，结果可能不同。

Oracle、PostgreSQL 等数据库通常默认使用读提交。InnoDB 也支持该级别。

#### 可重复读

可重复读是 InnoDB 的默认事务隔离级别。对于普通 `SELECT` 产生的快照读，同一个事务会复用一致性视图，因此其他事务在此期间提交的修改通常不会改变当前事务后续快照读的结果。

需要注意，“可重复读看到事务开始时的数据”是一种便于理解但不够精确的说法：InnoDB 通常在事务的**第一次快照读**时创建 Read View，而不一定在执行 `BEGIN` 的瞬间创建。使用下面的语句可以在事务开始时立即创建一致性快照：

```sql
START TRANSACTION WITH CONSISTENT SNAPSHOT;
```

此外，事务总能看到自己已经完成的修改；`SELECT ... FOR UPDATE` 等当前读也不会使用旧快照，而是读取最新可用版本并加锁。

#### 串行化

串行化提供最强的隔离能力。InnoDB 在该级别下会让普通读取更多地采用加锁方式：读操作使用共享锁，写操作使用排他锁。锁发生冲突时，后访问的事务需要等待前一个事务提交或回滚，因此可以避免前述读取异常，但吞吐量和并发能力也会明显下降。

### 用两个事务理解可见性

创建一张测试表，并写入初始值 `1`：

```sql
CREATE TABLE T(c INT) ENGINE = InnoDB;
INSERT INTO T(c) VALUES (1);
```

在两个会话中显式启动事务，然后按照以下顺序执行。这里的查询均为普通 `SELECT`：

| 执行顺序 | 事务 A | 事务 B |
| --- | --- | --- |
| 1 | `BEGIN;` | `BEGIN;` |
| 2 | `SELECT c FROM T;`，结果为 `1` | |
| 3 | | `SELECT c FROM T;`，结果为 `1` |
| 4 | | `UPDATE T SET c = 2;` |
| 5 | 再次查询，得到 `V1` | |
| 6 | | `COMMIT;` |
| 7 | 再次查询，得到 `V2` | |
| 8 | `COMMIT;` | |
| 9 | 在新事务中查询，得到 `V3` | |

在前三种隔离级别下，结果如下：

| 隔离级别 | V1：B 提交前 | V2：B 提交后、A 提交前 | V3：A 提交后 |
| --- | --- | --- | --- |
| 读未提交 | `2` | `2` | `2` |
| 读提交 | `1` | `2` | `2` |
| 可重复读 | `1` | `1` | `2` |

- **读未提交**允许 A 在 B 提交前就读到 `2`，这就是脏读。
- **读提交**下，A 在 B 提交前读到 `1`，B 提交后则读到 `2`，所以同一事务内两次查询结果不同。
- **可重复读**下，A 的快照读一直使用第一次查询建立的 Read View，因此提交前始终看到 `1`；A 提交后开启新的事务，才能看到 `2`。
- **串行化**下情况不同：A 的普通读取会持有共享锁，B 的更新需要排他锁，因此步骤 4 会被阻塞，必须等 A 提交后才能继续。也就是说，串行化通过等待直接消除了这个并发时序，不能简单套用上表的 V1、V2。

这个例子讨论的是快照读。若把 A 的查询改成 `SELECT ... FOR UPDATE`，它就变成当前读，行为和加锁范围都会发生变化。

### 从 Oracle 迁移时注意隔离级别

Oracle 的默认隔离级别是读提交，而 InnoDB 的默认隔离级别是可重复读。应用从 Oracle 迁移到 MySQL 时，如果业务逻辑依赖读提交语义，应显式把 MySQL 配置为 `READ-COMMITTED`，否则同一事务中重复查询的可见性可能发生变化。

可以在配置文件中设置默认级别：

```ini
[mysqld]
transaction_isolation = READ-COMMITTED
```

也可以先在会话级验证：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

不过，隔离级别一致并不代表两种数据库的事务行为完全相同。迁移时还需要测试锁范围、并发更新、空值处理和 SQL 语义等差异。

### 查看和修改 MySQL 隔离级别

可以通过以下语句查看当前会话的事务隔离级别：

```sql
SELECT @@transaction_isolation;
```

修改当前会话后续事务的隔离级别：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

隔离级别会直接影响事务读取数据的方式。修改生产环境配置前，需要结合一致性要求、锁竞争和应用逻辑进行评估。

## MVCC

MVCC 的全称是 **Multi-Version Concurrency Control（多版本并发控制）**。它让数据库为一行数据维护多个历史版本，使读事务可以读取符合自身可见性规则的版本，而不必与正在修改数据的事务互相阻塞。

MVCC 的核心价值可以概括为：**读不阻塞写，写不阻塞普通的快照读**。不过，写操作之间以及加锁读取之间仍然需要使用锁进行并发控制。

### 快照读与当前读

在 InnoDB 中，读取大致可以分为两类：

- **快照读（Consistent Read）**：普通 `SELECT` 通常属于快照读。它根据 Read View 从版本链中选择一个可见的数据版本，一般不会对读取到的记录加行锁。
- **当前读（Current Read）**：读取记录的最新可用版本，并根据操作类型加锁。`UPDATE`、`DELETE`、`INSERT`、`SELECT ... FOR UPDATE` 和 `SELECT ... FOR SHARE` 都需要当前读。

MVCC 主要解决快照读的并发问题；当前读和数据修改仍要依赖行锁、间隙锁及 Next-Key Lock 等锁机制。

### 版本链如何形成

InnoDB 的聚簇索引记录中包含用于 MVCC 的隐藏信息，其中最重要的是：

- **DB_TRX_ID**：最后一次插入或修改该记录的事务 ID。
- **DB_ROLL_PTR**：回滚指针，指向 undo log 中的上一个历史版本。

当事务修改一行数据时，InnoDB 会把修改前的信息写入 undo log，并更新记录上的事务 ID 和回滚指针。多个历史版本通过回滚指针连接起来，形成一条版本链。

版本链并不是在数据页里保存许多完整副本，而是由当前记录配合 undo log 还原出历史版本。旧版本也不会永久保留：当系统确认已经没有 Read View 需要访问它们时，Purge 线程会逐步清理相应的 undo 记录。

### Read View 如何判断版本是否可见

Read View 可以理解为事务进行快照读时生成的一张“活跃事务名单”。它记录创建快照时仍未提交的事务，并结合当前事务 ID、活跃事务 ID 的边界等信息，判断版本链中的某个版本是否对当前事务可见。

判断过程可以简化为：

1. 当前事务自己生成的版本，对自己可见；
2. 创建 Read View 之前已经提交的版本，通常可见；
3. 创建 Read View 时仍然活跃、之后才提交的事务版本，对该 Read View 不可见；
4. 如果当前版本不可见，就沿着 `DB_ROLL_PTR` 查找更早的版本，直到找到可见版本或版本链结束。

因此，即使另一事务已经修改并提交了某行数据，持有较早 Read View 的事务仍可能沿着 undo log 读到修改前的版本。

### undo log 什么时候可以清理

undo log 是否能被清理，需要同时考虑**事务回滚**和**一致性读**：

1. 事务尚未结束时，它产生的 undo log 必须保留，因为事务仍可能回滚；
2. 事务提交后，用于 `UPDATE` 和 `DELETE` 的 undo log 仍可能被较早的 Read View 用来还原历史版本；
3. InnoDB 会关注系统中最老的活跃 Read View。只要某段历史版本仍可能被这个视图或更新的视图访问，Purge 就不能清理它；
4. 当修改事务已经提交，并且所有可能访问该旧版本的 Read View 都已经结束后，相应的 undo 记录和被删除标记的记录才具备清理条件；
5. Purge 线程异步推进清理，所以“具备清理条件”不等于磁盘空间会立即缩小。

简化来看，**系统中最老的 Read View 决定了 Purge 能够向前推进到哪里**。一个很早创建但迟迟不结束的 Read View，会像一道水位线一样挡住它之后积累的大量历史版本。

`INSERT` undo 通常只用于回滚当前插入操作，事务提交后便不再需要为其他事务提供旧版本；`UPDATE` undo 则还承担 MVCC 历史版本的职责，提交后也可能继续保留。

### 读提交与可重复读的 MVCC 差异

读提交和可重复读都可以使用 MVCC，它们最关键的区别是 **Read View 的创建时机不同**：

- **读提交**：每条快照读语句通常都会创建新的 Read View，所以能够看到语句开始前其他事务已经提交的修改。
- **可重复读**：事务中的第一次快照读创建 Read View，之后的快照读通常复用它，因此多次读取能够保持一致。

假设事务 A 先查询某行数据，事务 B 随后修改该行并提交：在读提交级别下，事务 A 再次查询时通常可以看到新值；在可重复读级别下，事务 A 的快照读通常仍然看到旧值。

### MVCC 与锁如何配合

“事务隔离由 MVCC 实现”并不完整。InnoDB 实际上通过 **MVCC 与锁机制共同实现事务隔离**：

- MVCC 为普通快照读提供一致的数据视图，减少读写阻塞；
- 行锁协调多个事务对同一记录的修改；
- 间隙锁和 Next-Key Lock 在可重复读级别下保护索引范围，避免当前读期间有其他事务插入新的匹配记录；
- 串行化级别通过更严格的加锁规则换取更强的隔离性。

因此，MVCC 并不意味着数据库不需要锁。它优化的是读写并发，而涉及写写冲突、当前读和范围一致性时，锁仍然不可替代。

## 为什么要避免长事务

长事务最直接的问题是阻碍 undo 历史版本的清理。尤其是在可重复读级别下，一旦事务建立了较早的 Read View，为了保证它后续仍能读到相同快照，Purge 就必须保留该视图可能访问的历史版本。

与此同时，其他事务还在不断更新数据，于是可能出现以下连锁反应：

- undo log 和 History List Length 持续增长；
- undo 表空间占用增加，Purge 清理压力变大；
- 读取旧版本时需要遍历更长的版本链；
- 长事务执行过的更新可能长期持有行锁，阻塞其他事务；
- 锁等待和死锁概率上升，严重时会影响整个实例的吞吐和可用性；
- 故障恢复和主从复制追赶可能需要处理更多事务数据。

并不是所有“连接存在很久”的会话都会阻塞 Purge。真正需要重点关注的是：长时间未提交的读写事务，以及已经建立一致性 Read View 的长时间快照事务。

### MySQL 5.5 与当前版本的 undo 存储差异

MySQL 5.5 中，rollback segment 在物理上属于 InnoDB 系统表空间，undo log 与旧版 InnoDB 数据字典等内部结构一起存放在 `ibdata` 系列文件中，常见的就是 `ibdata1`。即使 undo 历史后来被清理，系统表空间已经增长的文件通常也不会自动缩回原来的大小。

以当前长期支持版本 MySQL 8.4 为例，实例初始化时默认创建两个独立 undo 表空间，数据文件通常为 `undo_001` 和 `undo_002`。现代版本还支持独立 undo 表空间的自动截断及在线管理，因此 undo 不再默认与数据字典一起挤在 `ibdata1` 中。

| 版本 | undo 默认位置 | 数据字典 | 空间治理能力 |
| --- | --- | --- | --- |
| MySQL 5.5 | InnoDB 系统表空间，通常是 `ibdata1` | 旧版 InnoDB 数据字典也在系统表空间 | 清理后文件通常不会自动收缩 |
| MySQL 8.4 | 两个默认独立 undo 表空间：`undo_001`、`undo_002` | MySQL 8.0 起使用事务型数据字典 | 支持自动截断及创建、停用、删除用户 undo 表空间 |

独立 undo 表空间改善了空间管理，但不会消除长事务的影响：只要旧版本仍被活跃事务需要，Purge 就不能清理它们。

## 事务的启动与结束

如果要手动管理一个包含多条语句的事务，常见方式有两种。

### 显式启动事务

使用 `BEGIN` 或 `START TRANSACTION` 显式开启事务，并用 `COMMIT` 或 `ROLLBACK` 明确结束：

```sql
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

这种方式能够清楚地标记事务边界，通常更适合业务代码。

### 关闭自动提交

执行下面的语句后，当前会话进入持续的手动提交模式：

```sql
SET autocommit = 0;
```

此后执行一条访问事务表的语句就可能启动事务，而且不会自动提交。事务会一直持续到显式执行 `COMMIT`、`ROLLBACK` 或连接断开。应用如果忘记提交，很容易产生长事务。因此通常建议保持 `autocommit = 1`，需要多语句事务时再使用 `BEGIN` 显式启动。

在 `autocommit = 1` 的情况下，每条未放入显式事务的语句本身仍是一个自动提交事务，并不是“没有事务”。

### 使用 COMMIT AND CHAIN

对于需要连续执行多个事务、又希望明确保留事务边界的业务，可以使用：

```sql
COMMIT WORK AND CHAIN;
```

它会提交当前事务，并立即以相同的事务特征启动下一个事务，从而省去再次发送 `BEGIN` 的交互。相比长期设置 `autocommit = 0`，这种写法更容易让开发者判断当前语句是否处于显式事务中。

## 查询持续时间超过 60 秒的事务

`INFORMATION_SCHEMA.INNODB_TRX` 展示当前正在 InnoDB 内部执行的事务。下面的语句可以找出持续时间超过 60 秒的事务：

```sql
SELECT
    trx_id,
    trx_mysql_thread_id,
    trx_state,
    trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS trx_seconds,
    trx_rows_locked,
    trx_rows_modified,
    trx_query
FROM information_schema.innodb_trx
WHERE trx_started < NOW() - INTERVAL 60 SECOND
ORDER BY trx_started;
```

排查时不能只看 `trx_query`。事务可能处于空闲状态，此时该字段可能为 `NULL`，但事务本身仍然没有结束。可以使用 `trx_mysql_thread_id` 关联 `performance_schema.threads`、`performance_schema.events_statements_current` 或会话列表，进一步确认连接来源与最后执行的语句。

## 小结

四种隔离级别规定了事务之间能够看到什么数据；MVCC 和锁则是 InnoDB 实现这些隔离语义的主要手段。

- 读未提交允许看到其他事务尚未提交的修改；
- 读提交为每条快照读创建新的数据视图；
- 可重复读通常在事务内复用 Read View，是 InnoDB 的默认级别；
- 串行化主要依靠更严格的加锁规则保证最强隔离；
- MVCC 通过隐藏字段、undo log、版本链和 Read View 提供非阻塞快照读；
- 当前读和数据修改仍然需要锁机制参与；
- 最老的活跃 Read View 会限制 Purge 的推进，因此应避免长事务；
- 建议保持自动提交开启，并通过显式事务语句清楚地控制事务边界。
