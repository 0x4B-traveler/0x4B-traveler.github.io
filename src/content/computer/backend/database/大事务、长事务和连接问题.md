## 连接问题

业务高峰期，生产环境中的 MySQL 可能因为瞬时流量、慢 SQL、锁等待或连接风暴失去响应。此时最重要的不是立刻把某个参数调大，而是先判断：数据库究竟是**没有连接名额了**，还是**已经进入执行过载**。

这两种现象可能同时发生，但处理方向不同：

- `Threads_connected` 接近 `max_connections`，大量连接处于 `Sleep`，说明连接名额可能被空闲会话占满；
- `Threads_running` 持续很高，CPU、I/O 或锁等待已经饱和，说明真正的问题是并发执行过多；
- 如果两者都高，继续放入更多连接往往只会增加上下文切换、内存占用与资源竞争，让雪崩更严重。

### 短连接风暴为什么代价很高

短连接模型是指应用频繁地建立连接、执行少量 SQL，然后马上断开。一次 TCP 连接的建立不只包含网络层的三次握手，还可能包括：

1. TCP 建连以及可选的 TLS 握手；
2. MySQL 协议握手与身份认证；
3. 解析账号、主机匹配、角色和权限信息；
4. 分配连接缓冲区及其他会话资源；
5. 建立或复用服务端连接线程；
6. 执行应用设置字符集、时区、隔离级别等会话初始化操作。

更准确地说，连接阶段会完成身份认证并建立会话安全上下文；具体 SQL 的对象权限还会在语句执行时检查，而不是在建连时一次性“获得整个连接的读写权限”。

MySQL 默认采用 `one-thread-per-connection` 模型：每个客户端连接关联一个服务端线程，由该线程处理认证和请求。这里的 “processlist ID” 是 **MySQL 连接/线程标识**，不是一个独立的操作系统进程。所有连接都位于同一个 `mysqld` 服务端进程中。启用服务端 Thread Pool 后，连接和实际执行线程之间不再固定为一一对应。

MySQL 会通过 `thread_cache_size` 缓存已经结束连接所使用的线程，减少反复创建和销毁操作系统线程的成本。但线程缓存无法省掉网络握手、认证、会话初始化等成本，所以解决短连接风暴的根本手段仍然是**在应用端复用连接并控制并发**。

### `max_connections` 不是越大越好

`max_connections` 控制普通接口允许同时存在的客户端连接数。达到上限后，新连接会收到：

```
Too many connections
```

MySQL 还会为具有 `CONNECTION_ADMIN` 权限的管理员保留一个额外连接名额，便于在普通连接已经满时进入实例诊断。MySQL 8.0.14 以后还支持通过 `admin_address` 和 `admin_port` 配置独立管理接口，生产环境可以提前规划这条应急通道。

可以先查看连接上限和实时状态：

```sql
SHOW VARIABLES LIKE 'max_connections';

SHOW GLOBAL STATUS
WHERE Variable_name IN (
  'Threads_connected',
  'Threads_running',
  'Threads_cached',
  'Threads_created',
  'Connections',
  'Aborted_connects',
  'Connection_errors_max_connections'
);
```

几个指标的含义如下：

- `Threads_connected`：当前打开的客户端连接数量；
- `Threads_running`：当前没有休眠、正在执行或等待执行资源的线程数量；
- `Threads_created`：实例启动后为处理连接创建过的线程数量；
- `Connections`：累计连接尝试次数；
- `Connection_errors_max_connections`：因为超过连接上限而失败的连接次数。

临时调大上限可以使用：

```sql
SET GLOBAL max_connections = 800;
```

但这只是允许更多请求进入数据库，不会创造更多 CPU、内存或 I/O 能力。每个连接都可能申请会话缓冲区、持有事务和锁；并发运行线程过多还会增加调度与资源争用。因此，只有在确认服务器仍有资源余量、主要矛盾确实是空闲连接占满名额时，才适合**有限度、可回退地**提高该值，并同步限制应用连接池。

### 临时方案一：优先释放事务外空闲连接

当连接已经耗尽时，一个有损但相对可控的办法，是清理长时间不工作的连接。处理顺序应当是：

1. 优先处理事务外的长期 `Sleep` 连接；
2. 确认仍不足时，再评估事务内的空闲连接；
3. 不要只根据 `Sleep` 状态批量终止，因为 `Sleep` 只表示当前没在执行 SQL，不代表它没有打开事务。

可以把连接列表与 `INFORMATION_SCHEMA.INNODB_TRX` 关联起来：

```sql
SELECT
  p.ID,
  p.USER,
  p.HOST,
  p.DB,
  p.COMMAND,
  p.TIME AS idle_seconds,
  p.STATE,
  trx.TRX_ID,
  trx.TRX_STARTED,
  trx.TRX_STATE,
  trx.TRX_ROWS_MODIFIED
FROM performance_schema.processlist AS p
LEFT JOIN information_schema.innodb_trx AS trx
  ON trx.TRX_MYSQL_THREAD_ID = p.ID
WHERE p.COMMAND = 'Sleep'
  AND p.ID <> CONNECTION_ID()
ORDER BY
  (trx.TRX_ID IS NOT NULL),
  p.TIME DESC;
```

结果中 `TRX_ID IS NULL` 的连接没有出现在当前 InnoDB 活跃事务列表中，可以优先检查；存在 `TRX_ID` 的连接则位于事务内，可能仍持有行锁、保留 undo 版本并阻塞 purge。需要注意，这些系统视图反映的是快速变化的瞬时状态，从查询到执行处置之间可能已经发生变化，不能把生成的 ID 长时间保存后再盲目执行。

也可以先使用：

```sql
SHOW FULL PROCESSLIST;
```

但在连接很多的繁忙实例上，更推荐查询基于 Performance Schema 的 `processlist` 或 `threads` 表，避免传统进程列表实现带来的额外互斥开销。

确认目标以后，终止连接的语法是：

```sql
KILL CONNECTION 12345;
```

`KILL CONNECTION` 会终止该连接正在执行的语句，然后断开整个会话。如果会话中存在未提交事务，连接关闭会触发事务回滚。大事务的回滚可能持续很久并继续消耗 I/O 和 CPU，所以“杀连接”不一定能立即降低负载，批量终止大事务甚至可能让压力进一步升高。

另一条命令是：

```sql
KILL QUERY 12345;
```

它只终止当前语句而保留连接。对于显式事务，这可能使事务继续存活并继续持锁，因此不能把它当作释放连接或结束事务的替代方案。

### 为什么客户端不一定马上知道连接已断开

服务端执行 `KILL CONNECTION` 后，客户端能否立即感知，取决于它此时是否正在读写 socket、驱动实现以及连接池的探活策略。空闲客户端通常要等到下一次使用连接时，才会看到类似错误：

```
Lost connection to MySQL server during query
```

也可能表现为：

```
MySQL server has gone away
```

如果应用拿着已经失效的连接句柄不断重试，而连接池又不丢弃并重建该连接，从业务侧看就会像“数据库一直没有恢复”。因此，DBA 执行断连前应确认应用具备以下能力：

- 识别连接级错误并废弃失效句柄；
- 重新从连接池获取或创建连接；
- 使用指数退避和抖动，避免所有实例同时重连；
- 只对幂等操作进行自动重试，或使用业务幂等键保护写请求；
- 设置合理的连接、读写和获取连接池连接超时。

### 空闲超时能做什么

`wait_timeout` 控制非交互连接保持空闲的时间，`interactive_timeout` 面向带有交互标志的客户端。适当降低超时可以减少连接长期泄漏，但它不是高峰期立即清理所有存量连接的按钮：全局值通常用于初始化之后建立的新会话，已有会话保留自己的 session 值。

超时设置过小还会导致正常低频连接反复断开和重建，反而制造短连接风暴。因此，更优先的做法是修复连接泄漏、限制连接池规模，并让连接池的最大生命周期和空闲回收时间与服务端配置协调。

### 临时方案二：`--skip-grant-tables` 不应作为性能止血手段

使用下面的参数重启 MySQL，会让服务器启动时不加载授权表：

```
--skip-grant-tables
```

这会绕过身份认证和权限检查，确实减少了相关过程，但其安全风险远远大于可能节省的连接开销，而且重启本身会扩大故障影响。因此，它的合理用途是**在隔离环境中恢复遗失的管理员账号或修复授权表**，不应被视为生产高峰期的性能优化方案。

MySQL 8.0/8.4 在启用 `--skip-grant-tables` 时会同时启用 `skip_networking`，禁止 TCP/IP 远程连接，只允许通过 Unix socket、Windows 命名管道或共享内存等本地接口访问。这降低了远程攻击面，但并没有消除风险：能够登录数据库主机并访问本地接口的用户仍可能在没有数据库认证的情况下取得高权限。

此外，该模式还会影响依赖授权表或 `mysql` 系统库加载的能力，例如部分插件、计划事件及登录失败跟踪。恢复完成后应执行 `FLUSH PRIVILEGES` 重新加载授权表，并尽快以正常方式重启或恢复配置。

结论很明确：**不要为了减少建连认证开销，在生产高峰期启用 `--skip-grant-tables`。** 正确方向是连接复用、入口限流、连接池配额、慢 SQL 和锁等待治理。

## 风险治理

### 高峰期连接故障的止血顺序

发生连接风暴时，可以按照下面的顺序处置：

1. **保护现场**：记录连接数、运行线程数、CPU、I/O、锁等待、慢 SQL 和应用错误率；
2. **入口减压**：在网关或应用侧限流，暂停报表、批处理和非核心任务，避免持续制造新连接；
3. **控制重连**：为连接建立失败增加指数退避与随机抖动，防止重连风暴；
4. **回收无事务空闲连接**：确认连接用途后，优先清理事务外长期 `Sleep` 会话；
5. **谨慎处理事务内连接**：评估锁、修改量和回滚成本，再决定是否终止；
6. **有限度提高连接上限**：仅在资源仍有余量时使用，并设置明确回退值；
7. **持续观察**：关注 `Threads_running`、错误率、P99 延迟和回滚线程，确认系统是真的恢复而不是把拥塞向后推迟。

### 长期治理方向

临时止血结束后，应回到根因治理：

- 使用连接池复用连接，并为每个应用设置合理的最小、最大连接数；
- 按实例容量为所有应用分配连接预算，避免各连接池上限之和远超数据库容量；
- 为建连失败和 SQL 重试配置退避、熔断与幂等保护；
- 监控 `Threads_connected`、`Threads_running`、`Threads_created` 和连接拒绝次数；
- 排查慢 SQL、锁等待、长事务和连接泄漏；
- 为 DBA 配置独立且最小权限的应急账号，必要时规划管理端口；
- 通过压测确定数据库的安全并发区间，而不是直接把 `max_connections` 当作容量指标。

数据库已经过载时，最有效的临时性能优化通常不是“让更多请求进来”，而是**减少无效工作、控制并发，并让系统恢复到可处理的负载区间**。
