## 一、操作系统：页表、缺页与写时复制

### 1. 页表解决什么问题

程序使用的是虚拟地址，内存条使用的是物理地址。操作系统为每个进程提供独立的虚拟地址空间，再通过页表把虚拟页号映射到物理页框号：

```text
虚拟地址 = 虚拟页号 + 页内偏移
                         │
                         ▼
页表项（PTE）：虚拟页号 ──> 物理页框号 + 权限/状态
                         │
                         ▼
物理地址 = 物理页框号 + 页内偏移
```

页内偏移不会因为映射而改变。假设页大小为 4 KiB，虚拟地址 `0x12345` 可以拆成虚拟页号和页内偏移；页表只负责把虚拟页号换成物理页框号，`0x345` 这样的页内偏移保持不变。

页表的主要作用有三点：

1. **地址隔离**：不同进程可以使用相同的虚拟地址，但映射到不同的物理内存，进程不能直接访问别人的地址空间。
2. **权限控制**：页表项可以标记可读、可写、可执行、用户态可访问等权限。
3. **虚拟内存**：进程看到的地址空间可以大于当前物理内存；暂时不用的页面可以被换出，需要时再装入。

#### 页表项是什么数据结构

页表不是一个简单的“虚拟地址到物理地址”的字典，而通常是按层级组织的数组。以常见的多级页表为例，虚拟地址被拆成多个索引，依次查找顶级页表、中间页表，最后找到页表项（Page Table Entry，PTE）。

一个 PTE 通常包含：

- 物理页框号（PFN）：页面实际位于哪个物理页框；
- `Present/Valid`：当前映射是否有效、页面是否在内存中；
- `R/W`：是否允许写入；
- `U/S`：用户态还是内核态可访问；
- `NX/XD`：是否禁止执行；
- `Accessed`：页面是否被访问过；
- `Dirty`：页面是否被写过，换出时可据此判断是否需要回写；
- 在换出、共享或写时复制场景中使用的其他状态位。

实际的页表项由硬件架构定义，字段名称和位数会不同。为了避免每次访问都走多级页表，处理器还会使用 TLB 缓存最近的虚拟页到物理页框映射。TLB 命中时可以快速完成地址转换；TLB 未命中时才需要进行页表遍历。

### 2. 什么是缺页

当 CPU 访问某个虚拟页面时，如果页表项显示页面不在物理内存中，或者访问权限不满足，例如向只读页写入，处理器会触发缺页异常（page fault）。这里的“缺页”不一定只意味着“页面被换出”，也可能是第一次访问一个尚未实际分配物理页的合法虚拟地址，或者是一次权限检查失败。

严格地说，缺页是由当前指令引起的**同步异常**，不是外部设备随机产生的异步中断。处理流程可以概括为：

1. CPU 发现页表项无效或权限不符，保存现场并进入内核异常处理流程；
2. 操作系统检查访问是否合法；
3. 如果页面在交换区，分配空闲页框并从磁盘读回；如果是合法的懒分配，则分配并清零一个物理页；
4. 更新页表和 TLB，重新执行导致异常的那条指令；
5. 如果地址根本不属于进程或权限不允许，则终止访问，用户程序可能收到 `SIGSEGV`。

#### 例子：懒分配

程序申请一块很大的堆空间时，操作系统可以先只记录“这段虚拟地址可以使用”，不立即为每一页分配物理内存。程序第一次写入其中某一页时发生缺页，内核才真正分配页框并建立映射。这把分配成本推迟到了实际使用时，但第一次访问会多出异常处理和可能的内存初始化开销。

### 3. 写时复制（Copy-on-Write，COW）

写时复制的核心是：**多个执行主体先共享同一份只读物理页，只有某一方真正写入时，操作系统才复制出一份私有页**。

典型场景是 Unix 的 `fork()`：子进程刚创建时不需要立刻复制父进程全部内存，父子进程的页表可以暂时指向相同物理页，并把这些页标记为只读。任意一方尝试写入时触发缺页异常，内核完成以下操作：

```text
父子进程共享只读页
        │ 子进程写入
        ▼
缺页异常 -> 分配新页 -> 复制原内容 -> 修改写方页表 -> 继续执行
```

优点包括：

- `fork()` 初始速度更快，因为不必立即复制全部内存；
- 节省物理内存，未被修改的页面可以一直共享；
- 如果子进程很快执行 `exec()`，原来的共享页几乎无需复制，收益尤其明显。

代价和边界也要说清楚：第一次写共享页会产生缺页处理和复制开销；如果父子进程都大量修改内存，最终仍可能接近完整复制的内存成本；共享页的引用计数、页表权限和异常处理也会增加操作系统实现复杂度。

## 二、HTTP 与 HTTPS：连接、加密与认证

### 1. 一句话区别

HTTPS 可以理解为 **HTTP over TLS**：HTTP 负责请求和响应的语义，TLS 在其下方提供加密传输、完整性校验和服务器身份认证。HTTP 本身通常是明文传输，HTTPS 则保护应用层数据不被中途直接读取或篡改。

典型连接顺序是：

```text
TCP 三次握手 -> TLS 握手（协商、认证、密钥交换） -> HTTP 请求/响应
```

因此，不能说“第一次建立 TCP 连接时使用非对称加密”。TCP 连接先建立；随后 TLS 握手通常使用证书和非对称密码完成身份认证与密钥协商，握手结束后，HTTP 数据通常使用对称会话密钥加密。

### 2. 对称加密与非对称加密

| 类型 | 做法 | 优点 | 缺点 | 常见用途 |
| --- | --- | --- | --- | --- |
| 对称加密 | 加密和解密使用同一个密钥，如 AES、ChaCha20 | 速度快、计算和带宽开销小，适合大量数据 | 双方要安全地共享密钥；多人通信时密钥管理复杂 | TLS 握手后的应用数据 |
| 非对称加密 | 使用公钥和私钥，如 RSA、ECC | 公钥可以公开，便于身份认证和密钥协商；私钥不必直接传给对方 | 运算较慢，密文或签名开销相对更大，不适合加密大量业务数据 | 证书签名、身份认证、密钥交换 |

现代 TLS 并不是简单地“用 RSA 加密所有内容”。TLS 1.3 常使用基于椭圆曲线的临时密钥交换（例如 ECDHE）建立共享密钥，再使用 AEAD 对称算法保护应用数据。临时密钥还可以提供前向保密：即使服务器长期私钥以后泄露，过去抓取的会话流量也不应因此被直接解密。

#### 面试实例：访问 HTTPS 网站

浏览器先与服务器完成 TCP 建连。TLS 握手中，服务器发送证书，浏览器验证证书链、域名和有效期；双方再通过密钥交换得到本次连接的会话密钥。之后浏览器发送的 `GET /` 和服务器返回的 HTML，都使用对称加密并带完整性校验。攻击者即使截获数据包，也不能直接看到请求内容或伪造一份能通过校验的响应。

HTTPS 并不保证服务器业务逻辑正确，也不自动解决终端被入侵、密码泄露或应用层越权问题；它解决的是传输链路上的机密性、完整性和身份认证问题。

## 三、Python 协程：把等待时间交还给事件循环

Python 协程是一种可以暂停和恢复的函数执行单元。使用 `async def` 定义协程函数，调用它得到的是 coroutine object；只有被事件循环调度（例如通过 `asyncio.run()` 或 `await`）后，函数体才会真正运行。

协程通常采用**协作式调度**：执行到 `await` 时主动暂停，把控制权交还给事件循环；事件循环可以在等待网络、文件或定时器期间运行其他就绪协程。它不是自动创建一个线程，也不等于多核并行。

```python
import asyncio


async def fetch(name: str, delay: float) -> str:
    await asyncio.sleep(delay)  # 模拟网络 I/O；这里不会阻塞整个事件循环
    return f'{name} done'


async def main() -> None:
    results = await asyncio.gather(
        fetch('api-a', 1),
        fetch('api-b', 1),
    )
    print(results)


asyncio.run(main())
```

两个任务都等待约 1 秒，因此整体耗时接近 1 秒，而不是简单相加为 2 秒。适合协程的场景是大量 I/O 等待，例如异步 HTTP 请求、爬虫、聊天服务和长连接；不适合把纯 CPU 密集计算直接塞进事件循环，因为一个没有主动 `await` 的长计算会阻塞其他协程。CPU 密集工作通常需要多进程、线程池或专门的计算方案。

一个常见陷阱是：在协程中调用同步阻塞函数，例如 `time.sleep(1)` 或一个耗时的同步网络请求。这样会阻塞事件循环，破坏并发效果；应使用异步版本，或把阻塞工作放入线程池/进程池。

## 四、概率题：每个家庭一直生，直到生出男孩

题目设定：有无限多个家庭；每个家庭每天最多生一个孩子；每次生男孩和女孩的概率都是 `1/2`；生出男孩后停止。问最终男女比例。

### 1. 先看一个家庭

一个家庭可能出现：

```text
男                 概率 1/2
女 -> 男            概率 1/4
女 -> 女 -> 男      概率 1/8
女 -> 女 -> 女 -> 男 概率 1/16
```

无论前面有多少个女孩，最后生男孩的概率都是 `1/2`。因此，一个家庭最终生出男孩的概率为 1（无限次都生不到男孩的概率趋近于 0），而在生出男孩之前，女孩数量服从参数为 `1/2` 的几何分布。

女孩数量的期望是：

```text
E(女孩数) = 0 × 1/2 + 1 × 1/4 + 2 × 1/8 + 3 × 1/16 + ... = 1
```

所以，一个家庭平均有 1 个女孩和 1 个男孩。这里的“平均”不是说每个家庭都恰好一男一女，而是说大量家庭合计后，女孩和男孩的数量会稳定接近这个比例。

### 2. 大量家庭的直觉

假设观察 100 个家庭：约有 50 个家庭第一胎就是男孩，它们贡献 50 个男孩；剩下约 50 个家庭会继续生，约 25 个家庭第二胎生男孩，并贡献 25 个女孩；再剩下约 25 个家庭继续生，约 12.5 个家庭第三胎生男孩，并贡献更多女孩。每一轮“留下来继续生”的家庭大约减半，但男孩和女孩的总量会分别累积成相同的期望数量。

因此，在独立同分布、男女概率确实各为 `1/2`，并且家庭数量足够大的理想模型中，最终男女比例是 **1:1**。无限家庭只是让大数定律的稳定效果更明显；它不意味着每个家庭的孩子数量无限，也不意味着每个家庭都男女各半。

### 3. 面试时可以这样回答

> 每个家庭一直生到第一次生男孩为止。对于单个家庭，男孩最终出现的概率是 1；在男孩之前的女孩数量期望为 `q/p = (1/2)/(1/2) = 1`，所以每个家庭平均贡献 1 个女孩和 1 个男孩。大量家庭汇总后，男女总数趋近 1:1。这个结论依赖于每胎独立且男女概率都是 50%；如果男女概率不是 50%，比例就不再是 1:1。

## 最后整理成四条主线

- 页表把虚拟地址映射到物理地址，并携带权限与状态；缺页是访问触发的同步异常；写时复制把复制成本推迟到第一次写入。
- HTTPS 是 HTTP over TLS；TCP 先建连，TLS 再认证和协商密钥，应用数据主要使用对称加密保护。
- Python 协程通过 `await` 主动让出控制权，适合高并发 I/O，不会自动带来 CPU 并行。
- 生男孩停止的家庭模型中，女孩数期望为 1，男孩最终出现，故大量家庭的男女总数趋近 1:1。
